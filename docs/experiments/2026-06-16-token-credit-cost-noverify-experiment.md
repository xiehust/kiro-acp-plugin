# 实验报告(无宿主验证变体):直接使用 Claude Code (Opus 4.8) vs 通过 delegating-to-kiro 委派开发(委派后**不让主 agent 跑 pytest 验证**)—— Token 与成本对比

- 日期:**2026-06-16**
- 环境:Linux arm64 (AWS) / Claude Code 2.1.178 / kiro-cli 2.6.0 / kiro-acp-plugin v0.4.4
- 原始数据:`/tmp/kiro-exp-nv/`(运行产物、result JSON、ACP 计量日志、框架独立 pytest 验证日志)
- 对比基准:本报告与 `2026-06-12-token-credit-cost-experiment.md`(下称"原报告",含宿主验证的 B 臂)使用**同一套任务、同一定价、同一计量方法、同一插件版本 v0.4.4**,唯一变量是 **B 臂是否让主 agent 亲自验证**。

> **这次改了什么(唯一变量)**:原实验里 B 臂(委派)在 kiro 完成后,要求宿主主 agent **亲自读文件 + 跑 `python3 -m pytest -q` 验证,失败再回委派修复**。本次按需求把这一步去掉:**B 臂主 agent 只发一次 `kiro_prompt` 委派、信任 kiro 自己的测试结果、不读文件、不跑 pytest、报告完成即结束**。目的:省掉验证往返带来的宿主 token。A 臂(直接开发)完全不变。
>
> 注意区分两个"pytest":被去掉的是**主 agent(宿主 claude 进程)**的验证;实验框架(bash 脚本)在每次运行后仍会**独立**在工作区跑一次 pytest 作为质量闸门——它由框架执行、不消耗任何宿主 token,是我们在去掉宿主验证后仍能诚实衡量"委派质量到底有没有打折"的依据。

## 1. 实验目的

对比同一组编码任务在两种工作方式下的资源消耗与货币成本:

- **A 臂(直接开发)**:Claude Code headless(`claude -p`,模型 `claude-opus-4-8`)直接完成任务。
- **B 臂(纯委派,无宿主验证)**:Claude Code headless 加载 kiro-acp-plugin,被指示**不亲自写代码、也不亲自验证**,只通过一次 `kiro_prompt` 把实现整体委派给本地 kiro-cli 子代理(kiro 模型同为 `claude-opus-4.8`,插件默认值),由 kiro 自己跑测试直到通过,宿主信任其结果即结束。

对比口径:① 纯 Token(A 臂) vs Token + kiro credit(B 臂);② 货币成本。

## 3. 测量方法

| 量 | 来源 | 校验 |
|---|---|---|
| A/B 臂宿主 token(input / output / cache read / cache write 5m/1h) | `claude -p --output-format json` 的 `usage` 与 `modelUsage` 字段 | 用单价逐项重算与 `total_cost_usd` 吻合(全部 6 次差异 < $0.0001,见 §7) |
| B 臂 kiro credit | 通过 `KIRO_MCP_BIN` 注入 tee 包装脚本,截获 `kiro-cli acp` 全部 JSON-RPC 流量,累加 `_kiro.dev/metadata` 通知中的 `meteringUsage`(单位 credit,全精度浮点,每轮增量) | 与 kiro 官方计费计数器(`kiro-cli chat --no-interactive "/usage"`)交叉校验:计数器增量 128.26 − 123.25 = 5.01 vs 三次委派 ACP 计量和 5.0121,**误差 ≈ 0.002**(限于计数器两位小数精度) |
| 任务完成质量 | 每次运行结束后由实验**框架**(bash 脚本,非主 agent)独立在工作区执行 `python3 -m pytest -q` | 不依赖代理自述,也不消耗宿主 token |

控制变量:两臂同模型(Opus 4.8)、同任务文本、每次运行使用全新临时工作区与全新进程(B 臂每次独立拉起 bridge + kiro 进程)、顺序执行。**与原报告唯一的不同是 B 臂提示词去掉了"亲自验证 + 失败回委派"段,改为"信任 kiro 自测、不读文件、不跑 pytest"。**

## 6. 对比分析

### 6.1 纯 Token vs Token + credit

| 维度 | A 臂(3 任务合计) | B 臂(3 任务合计) | B 相对 A |
|---|---:|---:|---:|
| 宿主 token 总量 | 1,081,948 | 310,524 | **−71.3%** |
| 其中 output token(最贵项,$25/M) | 29,037 | 3,727 | **−87.2%** |
| 其中 cache read | 925,363 | 206,097 | **−77.7%** |
| 其中 cache write | 97,350 | 71,907 | **−26.1%** |
| input | 30,198 | 28,793 | −4.7% |
| kiro credits | 0 | 5.0121 | +5.01 credits |

解读:
- **去掉宿主验证后,委派把宿主端几乎所有"工作量"都转移到了 kiro 侧。** 宿主只剩 3–4 轮(发一次委派 + 收一次结果 + 报告),宿主 token 总量直降 **71%**、最贵的 output token 降 **87%**、cache read 降 **78%**。input 几乎不变(由任务提示词主导)。
- **cache write 这次反而下降 26%**(原报告含验证时 B 比 A 高 +39%)。原因正是 §6.1 解读所印证的——cache write 的高低主要由**往返轮次**决定:验证往返没了,轮数从 7–10 掉到 3–4,缓存重写也随之减少。这与原报告 §10.1 的纠正一致(cache write 差异来自委派行为/往返/TTL 重写时机,而非"插件装载")。
- 代价是 kiro credit:本组三次委派共 **5.01 credit**(合 $0.20)。注意本次 credit 比原报告(3.37 / 4.72)更高,主要是 **T2-B 这次 kiro 内部迭代更多**(9 个计量事件、2.48 credit);这是 kiro 侧的 run-to-run 噪声,**与"去掉宿主验证"无因果关系**(宿主验证只在失败时触发回委派,而前后两次都没有失败)。

## 8. 局限性

1. **样本量 n=1**:每个任务×臂只跑一次,LLM 轨迹随机。本次三任务"委派(无验证)省约一半"方向一致且幅度很大(−41% ~ −55%),但绝对数仍受单次缓存/轨迹影响,不宜对小数位过度解读。
2. **A 臂跨会话有波动**:本会话 A 臂总成本($2.03)高于原报告 v0.4.4 会话的 A($1.60),属缓存温度/轨迹的会话间差异——所以**本报告的清洁对比是"同一会话内 A vs B"(−48.5%)**;§6.3 的"B 含验证 vs B 无验证"是跨会话对比,只看数量级。
3. **质量结论的边界**:本组任务上"信任 kiro 自测"没有翻车,但**这是因为框架独立 pytest 恰好确认了 kiro 自测可靠**——它替代了被去掉的宿主验证,充当了事后质量闸门。详见 §9 的风险提示。
4. **缓存未严格控温**:各运行间隔的缓存命中率自然不同;两臂条件对称但未控温。
5. **计费视角**:token 成本按 API 牌价。若 Claude Code 走 Max 订阅、kiro credit 在套餐额度内,两侧边际货币成本都可能为 0,此时对比变为"消耗哪个池子的额度"。

## 9. 结论

1. **去掉主 agent 的 pytest 验证,委派的成本优势大幅放大**:同一会话内,B(纯委派、无宿主验证)比 A(直接开发)便宜 **~48.5%**(实际口径 $1.046 vs $2.031);相比原报告"含宿主验证只省 ~7.8%",省下的几乎全是**验证往返的宿主 token**。
2. **省的是最贵的那部分**:宿主 output token −87%、cache read −78%、宿主 token 总量 −71%;委派后宿主只剩 3–4 轮。cache write 这次**下降 26%**(因往返变少),进一步印证 cache write 由轮次而非"插件装载"驱动(呼应原报告 §10.1)。
3. **credit 仍是小头但占比升高**:三次委派共 5.01 credit($0.20),占 B 总成本 ~19%(原报告 ~9%)——是分母(宿主 token)被砍小所致,不是 credit 变贵。本次 credit 偏高主要来自 T2-B 的 kiro 内部多迭代,属 kiro 侧噪声,与去掉宿主验证无因果关系。
4. **本组任务质量没打折,但这依赖一个外部闸门**:框架独立 pytest 全绿(11/7/22),说明 kiro 自测可靠到不需要宿主再验。⚠️ **关键风险提示**:去掉宿主验证,等于撤掉了委派链路里宿主侧的安全网——正确性**完全押在 kiro 的自测上**。本实验里有"框架独立 pytest"兜底确认,但**真实使用中通常没有这个独立闸门**;一旦 kiro 自测不充分或误判通过,宿主将原样接受错误产物且无从发现。
5. **credit 计账干净**:无崩溃,计费计数器(128.26)= 基线(123.25)+ ACP 实时计量和(5.0121),误差 ≈ 0.002。

**实用建议**:
- **追求省 token**:委派后不让主 agent 验证,能把宿主成本砍掉约一半——对"可清晰描述验收标准、且你信任 kiro 自测"的实现型任务,这是真实且可观的节省。
- **追求稳妥**:保留宿主验证(原报告口径)。它吃掉了大部分成本优势(只剩省 ~8%),但换来一道宿主侧的独立质量闸门——尤其对没有外部 CI/测试兜底的关键产物。
- **折中**:让 kiro 自测 + 仅在高风险任务上让宿主做"轻量抽查"(只读关键文件、不跑全量测试),在成本与安全网之间取平衡。本实验的两端数据($1.05 无验证 ↔ $1.48 全验证)给出了这条折中线的成本区间。
