# 实验报告:直接使用 Claude Code (Opus 4.8) vs 通过 delegating-to-kiro 委派开发 —— Token 与成本对比

- 日期:2026-06-12 首跑;**2026-06-14 干净重跑(本报告数据)**
- 环境:Linux arm64 (AWS) / Claude Code 2.1.177 / kiro-cli 2.6.0 / kiro-acp-plugin v0.4.3
- 原始数据:`/tmp/kiro-exp/`(运行产物、result JSON、ACP 计量日志、pytest 验证日志);首跑的污染产物归档在 `/tmp/kiro-exp/archive/20260612-prev/`

> **重跑说明**:首跑(2026-06-12)中 T3-B 首次运行因宿主 `claude` CLI 的 Bun 段错误崩溃(详见 §6.4),崩溃发生在 kiro 已扣 credit 之后,使该轮已消耗的 credit 既无法归因到一次成功运行、也污染了 credit 计数器的交叉校验(计费计数器把崩溃次的 credit 也计入了)。为得到干净、内部一致的 credit 计账,2026-06-14 在全新基线下**一次性顺序重跑全部 6 次运行**,无任何崩溃,计数器与 ACP 计量和精确吻合(§7)。下文全部为重跑数据。

## 1. 实验目的

对比同一组编码任务在两种工作方式下的资源消耗与货币成本:

- **A 臂(直接开发)**:Claude Code headless(`claude -p`,模型 `claude-opus-4-8`)直接完成任务。
- **B 臂(委派开发)**:Claude Code headless 加载 kiro-acp-plugin,被指示**不亲自写代码**,通过 `kiro_prompt` MCP 工具把实现整体委派给本地 kiro-cli 子代理(kiro 模型同为 `claude-opus-4.8`,插件默认值),随后亲自验证(读文件 + 跑 pytest),失败则回delegation修复。

对比口径:
1. **纯 Token**(A 臂)vs **Token + kiro credit**(B 臂);
2. 货币成本。

## 2. 定价

| 项目 | 单价 |
|---|---|
| Opus 4.8 input | $5 / M token |
| Opus 4.8 output | $25 / M token |
| Opus 4.8 cache read | $0.5 / M token |
| Opus 4.8 cache write(5 分钟 TTL) | $6.25 / M token |

> 说明:任务给定的"cache write $6.25/M"对应 5 分钟 TTL。实测 Claude Code 的缓存写入混用 5m 与 1h 两档(result JSON 中 `cache_creation` 拆分可见),其自报 `total_cost_usd` 对 1h 档按 $10/M 计价(已逐条验算吻合)。下文同时给出两种口径:**用户公式成本**(全部缓存写按 $6.25/M)与 **实际口径成本**(5m/1h 分档,与 Claude 自报一致)。

## 3. 测量方法

| 量 | 来源 | 校验 |
|---|---|---|
| A/B 臂宿主 token(input / output / cache read / cache write 5m/1h) | `claude -p --output-format json` 的 `usage` 与 `modelUsage` 字段 | 用单价逐项重算与 `total_cost_usd` 吻合(差异 < $0.0001) |
| B 臂 kiro credit | 通过 `KIRO_MCP_BIN` 注入 tee 包装脚本,截获 `kiro-cli acp` 的全部 JSON-RPC 流量,累加 `_kiro.dev/metadata` 通知中的 `meteringUsage`(单位 credit,全精度浮点;实测确认为**每轮增量**而非累计) | 与 kiro 官方计费计数器(`kiro-cli chat --no-interactive "/usage"`)交叉校验:重跑后计数器增量(97.73 − 基线 94.36 = 3.37)vs 三次委派 ACP 计量和 3.3729,**误差 ≈ 0.003**(限于计数器两位小数精度;计数器有 1–3 分钟入账延迟) |
| 任务完成质量 | 每次运行结束后由实验框架**独立**在工作区执行 `python3 -m pytest -q` | 不依赖代理自述 |

控制变量:两臂同模型(Opus 4.8)、同任务文本、每次运行使用全新临时工作区与全新进程(B 臂每次运行独立拉起 bridge + kiro 进程)、顺序执行。B 臂提示词仅额外加入"必须委派、只做验证"的策略段。

## 6. 对比分析

### 6.1 纯 Token vs Token + credit

| 维度 | A 臂(3 任务合计) | B 臂(3 任务合计) | B 相对 A |
|---|---:|---:|---:|
| 宿主 token 总量 | 1,102,431 | 767,620 | **−30.4%** |
| 其中 output token(最贵项) | 16,145 | 5,606 | **−65.3%** |
| 其中 cache read | 980,592 | 625,381 | −36.2% |
| 其中 cache write | 80,976 | 112,839 | **+39.3%**(插件上下文装载) |
| kiro credits | 0 | 3.3729 | +3.37 credits |

解读:
- 委派把"实现过程"的全部中间 token(读写文件、跑测试、改错的多轮往返)转移到了 kiro 侧,宿主端 output token 下降约 2/3 —— 这是按 $25/M 计价的最贵项。
- 代价有两块:① kiro credit(本组任务每次委派 0.69–1.38 credit,合 $0.03–0.06);② 插件固定开销 —— 加载 kiro MCP 工具/技能使每次运行的 cache write 上升约 39%(约 $0.05–0.10),且委派提示词本身更长。

### 6.4 稳定性观察

**本次重跑 6/6 全部一次成功,无崩溃。**

作为对照,首跑(2026-06-12)4 次委派运行中有 1 次(T3-B 首次)宿主 `claude` CLI 在运行约 71 秒时因 **Bun 1.3.14 段错误崩溃**(exit 133,Bun 自身 bug,非插件代码路径)。崩溃发生在委派完成之后 —— kiro 已写完代码且独立 pytest 验证通过,但宿主端 usage JSON 丢失,且该次已消耗的 credit 无法退回,还把崩溃次的 credit 混入了计费计数器,导致首跑的 credit 交叉校验出现偏差(这正是本次重跑的动因)。这提示委派模式的一个真实风险面:**宿主进程失败不影响 kiro 已扣的 credit,且会污染按计数器口径的事后对账**;以 ACP 实时 `meteringUsage`(按成功运行逐轮记录)为准、并确保无崩溃,才能得到干净计账。该 Bun 崩溃为低频随机故障,本次重跑未复现。

## 7. 交叉校验记录

- 重跑前 kiro 计费基线:**94.36** credits(计数器已稳定,无在途用量);
- 三次委派(T1-B/T2-B/T3-B)各自 ACP 计量恰为 3 个 `credit` 计量事件(每轮增量),逐次计量值:0.6925 / 1.3034 / 1.3769,计量和 = **3.3729**;
- 重跑结束终核:计费计数器 **97.73** = 基线 94.36 + 计量和 3.3729 = **97.7329**,与计数器小数精度(两位)**精确吻合,误差 ≈ 0.003**;
- 与首跑的关键差别:首跑因崩溃次把额外 credit 混入计数器,counter 口径需要"含崩溃次"才对得上(5.2826);本次无崩溃,counter 与"仅成功运行"的计量和直接吻合,计账干净无歧义。
- 计数器入账延迟约 1–3 分钟;ACP `meteringUsage` 为实时全精度值,实验以其为准。
- 宿主 token 成本:对全部 6 次运行,用单价重算(5m/1h 分档)与 `total_cost_usd` 自报值**完全吻合**(差异 < $0.0001,逐条已验)。

## 8. 局限性

1. **样本量 n=1**:每个任务×臂只跑一次。LLM 轨迹随机,单次差异 ±20% 内不宜过度解读 —— 本次重跑里 T1(小任务)的方向就与首跑相反(参见 §6.2),说明小任务两臂成本贴近、落在噪声内。但"宿主 output token 大幅下降(~65%)、cache write 上升(~39%)、中大任务委派更省"的结构性方向在两次实验、三个任务上一致。
2. **任务规模上限**:最大任务 T3 仍属"几分钟级"。委派的固定开销(插件上下文 + 验证)是常数,任务越大被摊薄越多 —— 本实验测得的 −17% 对更大任务可能是下限。
3. **计费视角**:token 成本按 API 牌价计算。若 Claude Code 走 Max 订阅、kiro credit 在 10,000/月套餐额度内,则两侧的**边际货币成本都可能为 0**,此时对比的意义变为"消耗哪个池子的额度"(本组任务的兑换比:每节省 ~$0.13 token 花费 ~1.3 credit)。
4. **缓存状态**:各运行间隔内缓存命中率自然不同;两臂条件对称但未严格控温。
5. **委派策略固定**:B 臂强制"整体委派 + 仅验证"。现实使用中宿主可能部分自己做,成本介于两臂之间。

## 9. 结论

1. **纯 Token 对比**:委派使宿主端 token 总量下降 ~30%,其中最贵的 output token 下降 ~65%;代价是 cache write(插件装载)上升 ~39% 和 3.37 个 kiro credit。
2. **成本对比**:三任务合计,委派方式便宜 **~7.8%**(实际口径 $1.477 vs $1.602)。分任务看,中大任务(T2/T3)委派更省的方向稳定;小任务(T1)两臂成本贴近、方向随机(本次 −8.6%,首跑 +14.8%),不宜据单次定论。
3. **credit 是小头**:委派总成本中 credit 仅占 ~9%($0.04/credit 下,每次委派 0.69–1.38 credit);决定成本的是宿主端 token,尤其是插件固定开销与验证轮次。
4. **质量不打折**:全部运行独立测试 100% 通过;测试覆盖深度在两臂间随轨迹波动,无稳定方向差异。
5. **credit 计账干净**:本次无崩溃,计费计数器(97.73)= 基线(94.36)+ ACP 实时计量和(3.3729),误差 ≈ 0.003。**这修正了首跑因 Bun 崩溃把崩溃次 credit 混入计数器造成的对账偏差** —— 该崩溃为低频随机故障,本次未复现,但它揭示的风险面真实存在:委派链路更长,宿主进程失败不影响 kiro 已扣的 credit,并会污染按计数器的事后对账。

**实用建议**:对几分钟以上、可清晰描述验收标准的实现型任务,委派给 kiro 在成本上有真实优势(且把 Opus 4.8 的 token 池换成 credit 池);对秒级小任务两种方式成本相当,直接做更省事。若要进一步压低委派成本,优化方向是减小插件固定上下文与验证开销,而不是 credit。
