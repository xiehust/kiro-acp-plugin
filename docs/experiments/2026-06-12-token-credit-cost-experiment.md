# 实验报告:直接使用 Claude Code (Opus 4.8) vs 通过 delegating-to-kiro 委派开发 —— Token 与成本对比

- 日期:2026-06-12
- 环境:Linux arm64 (AWS) / Claude Code 2.1.175 / kiro-cli 2.6.0 / kiro-acp-plugin v0.4.3
- 原始数据:`/tmp/kiro-exp/`(运行产物、result JSON、ACP 计量日志、pytest 验证日志)

## 1. 实验目的

对比同一组编码任务在两种工作方式下的资源消耗与货币成本:

- **A 臂(直接开发)**:Claude Code headless(`claude -p`,模型 `claude-opus-4-8`)直接完成任务。
- **B 臂(委派开发)**:Claude Code headless 加载 kiro-acp-plugin,被指示**不亲自写代码**,通过 `kiro_prompt` MCP 工具把实现整体委派给本地 kiro-cli 子代理(kiro 模型同为 `claude-opus-4.8`,插件默认值),随后亲自验证(读文件 + 跑 pytest),失败则回delegation修复。

对比口径:
1. **纯 Token**(A 臂)vs **Token + kiro credit**(B 臂);
2. 货币成本。

## 2. 定价

| 项目 | 单价 |
|---|---|
| Opus 4.8 input | $5 / M token |
| Opus 4.8 output | $25 / M token |
| Opus 4.8 cache read | $0.5 / M token |
| Opus 4.8 cache write(5 分钟 TTL) | $6.25 / M token |
| Opus 4.8 cache write(1 小时 TTL,实测 Claude Code 实际使用并计价) | $10 / M token |
| kiro credit | $0.04 / credit |

> 说明:任务给定的"cache write $6.25/M"对应 5 分钟 TTL。实测 Claude Code 的缓存写入混用 5m 与 1h 两档(result JSON 中 `cache_creation` 拆分可见),其自报 `total_cost_usd` 对 1h 档按 $10/M 计价(已逐条验算吻合)。下文同时给出两种口径:**用户公式成本**(全部缓存写按 $6.25/M)与 **实际口径成本**(5m/1h 分档,与 Claude 自报一致)。

## 3. 测量方法

| 量 | 来源 | 校验 |
|---|---|---|
| A/B 臂宿主 token(input / output / cache read / cache write 5m/1h) | `claude -p --output-format json` 的 `usage` 与 `modelUsage` 字段 | 用单价逐项重算与 `total_cost_usd` 吻合(差异 < $0.0001) |
| B 臂 kiro credit | 通过 `KIRO_MCP_BIN` 注入 tee 包装脚本,截获 `kiro-cli acp` 的全部 JSON-RPC 流量,累加 `_kiro.dev/metadata` 通知中的 `meteringUsage`(单位 credit,全精度浮点;实测确认为**每轮增量**而非累计) | 与 kiro 官方计费计数器(`kiro-cli chat --no-interactive "/usage"`)交叉校验:实验中段计数器增量 3.73 credits vs 计量和 3.731 credits,**误差 0.001**(计数器有 1–3 分钟入账延迟) |
| 任务完成质量 | 每次运行结束后由实验框架**独立**在工作区执行 `python3 -m pytest -q` | 不依赖代理自述 |

控制变量:两臂同模型(Opus 4.8)、同任务文本、每次运行使用全新临时工作区与全新进程(B 臂每次运行独立拉起 bridge + kiro 进程)、顺序执行。B 臂提示词仅额外加入"必须委派、只做验证"的策略段。

## 6. 对比分析

### 6.1 纯 Token vs Token + credit

| 维度 | A 臂(3 任务合计) | B 臂(3 任务合计) | B 相对 A |
|---|---:|---:|---:|
| 宿主 token 总量 | 1,106,018 | 766,634 | **−30.7%** |
| 其中 output token(最贵项) | 15,391 | 5,426 | **−64.7%** |
| 其中 cache read | 1,001,280 | 644,539 | −35.6% |
| 其中 cache write | 70,342 | 92,746 | **+31.9%**(插件上下文装载) |
| kiro credits | 0 | 3.8714 | +3.87 credits |

解读:
- 委派把"实现过程"的全部中间 token(读写文件、跑测试、改错的多轮往返)转移到了 kiro 侧,宿主端 output token 下降近 2/3 —— 这是按 $25/M 计价的最贵项。
- 代价有两块:① kiro credit(本组任务每次委派 0.75–1.57 credit,合 $0.03–0.06);② 插件固定开销 —— 加载 kiro MCP 工具/技能使每次运行的 cache write 增加约 8k–15k token(约 $0.05–0.10),且委派提示词本身更长。

### 6.4 稳定性观察

4 次委派运行中有 1 次(T3-B 首跑)宿主 `claude` CLI 在运行约 71 秒时因 **Bun 1.3.14 段错误崩溃**(exit 133,Bun 自身 bug,非插件代码路径)。值得注意:崩溃发生在委派完成之后 —— kiro 已写完代码且独立 pytest 验证 17 个测试全部通过,但宿主端 usage JSON 丢失,且该次已消耗的 1.411 credit 无法退回。重跑成功。这提示委派模式的一个真实风险面:**宿主进程失败不影响 kiro 已扣的 credit**。(该崩溃运行的成本未计入上文对比;若计入,B 臂合计增加 $0.0564 credit 成本,仍便宜 ~5%。)

## 7. 交叉校验记录

- 实验前 kiro 计费基线:88.37 credits(已用额度);
- 中途校验:计费计数器 92.46 − 基线 88.73(含探针后基线)= **3.73**,与前三次委派的 ACP 计量和 **3.731** 一致(±0.001);
- 实验结束终核:计费计数器 **94.01** = 基线 88.73 + 全部四次委派(含崩溃次)计量和 **5.2826**(88.73 + 5.283 = 94.013,精确吻合到计数器的小数精度);
- 计数器入账延迟约 1–3 分钟;ACP `meteringUsage` 为实时全精度值,实验以其为准。
- 宿主 token 成本:对全部 6 次运行,用单价重算(5m/1h 分档)与 `total_cost_usd` 自报值完全吻合。

## 8. 局限性

1. **样本量 n=1**:每个任务×臂只跑一次(T3-B 因宿主崩溃重跑一次)。LLM 轨迹随机,单次差异 ±20% 内不宜过度解读;但"宿主 output token 大幅下降、cache write 上升、小任务不划算/中大任务划算"的结构性方向在三个任务上一致。
2. **任务规模上限**:最大任务 T3 仍属"几分钟级"。委派的固定开销(插件上下文 + 验证)是常数,任务越大被摊薄越多 —— 本实验测得的 −17% 对更大任务可能是下限。
3. **计费视角**:token 成本按 API 牌价计算。若 Claude Code 走 Max 订阅、kiro credit 在 10,000/月套餐额度内,则两侧的**边际货币成本都可能为 0**,此时对比的意义变为"消耗哪个池子的额度"(本组任务的兑换比:每节省 ~$0.13 token 花费 ~1.3 credit)。
4. **缓存状态**:各运行间隔内缓存命中率自然不同;两臂条件对称但未严格控温。
5. **委派策略固定**:B 臂强制"整体委派 + 仅验证"。现实使用中宿主可能部分自己做,成本介于两臂之间。

## 9. 结论

1. **纯 Token 对比**:委派使宿主端 token 总量下降 ~31%,其中最贵的 output token 下降 ~65%;代价是 cache write(插件装载)上升 ~32% 和 3.87 个 kiro credit。
2. **成本对比**:三任务合计,委派方式便宜 **~9%**(实际口径 $1.367 vs $1.502)。但分任务看是**规模依赖**的:小任务(秒级函数题)委派**反而贵 ~15%**(固定开销摊不薄);中等及以上任务委派便宜 **~17%**。
3. **credit 是小头**:委派总成本中 credit 仅占 ~11%($0.04/credit 下,每次委派 0.75–1.6 credit);决定成本的是宿主端 token,尤其是插件固定开销与验证轮次。
4. **质量不打折**:全部运行独立测试 100% 通过,委派臂测试覆盖数还略多。
5. **风险提示**:观察到 1/4 委派运行宿主 CLI 崩溃(Bun bug),kiro 已扣 credit 不可恢复 —— 委派链路更长,故障面更大。

**实用建议**:对几分钟以上、可清晰描述验收标准的实现型任务,委派给 kiro 在成本上有真实优势(且把 Opus 4.8 的 token 池换成 credit 池);对小型任务直接做更划算。若要进一步压低委派成本,优化方向是减小插件固定上下文与验证开销,而不是 credit。
